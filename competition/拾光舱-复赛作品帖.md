复赛阶段的所有改造与新增功能，全程在 TRAE Work 中完成，没有借助任何其他 IDE。

## 二、产品简介（复赛版）

### 是什么

**拾光舱**（ShíGuāng Capsule）是一款基于 Electron 的跨平台桌面应用，支持 macOS 与 Windows，开箱即用、无需配置环境。它覆盖摄影师「出门前该不该去 → 拍完之后怎么归 → 几年后怎么找」的完整链路，让创作之外的收尾工作从一整晚缩短到一杯咖啡的时间。

相比初赛 Demo，复赛版本完成了**两次关键跃迁**：

1. **v1.0.1「可信归档 + 可检索仓库」**：从「会拷贝的工具」升级为「可信任的仓库」。新增 SHA-256 哈希校验、EXIF 时间归档、双盘镜像备份、EXIF 多维筛选、清单完整性校验，让每一张照片都可被信任、可被追溯、可被快速找到。
2. **v1.0.2「追光百宝箱」**：从「拍完之后才打开」升级为「出门之前就要打开」。新增独立页签，基于 Open-Meteo 气象数据 + suncalc 月相纯算法，对未来 7 天的雷暴、朝霞、晚霞、星轨四类天象做概率预测，把"凭经验蹲守"变成"按概率决策"。

### 面向谁

核心用户是**摄影爱好者**——刚入坑、还在用系统复制粘贴整理素材、蹲守天象全凭运气的那批人；次级用户包括旅拍 / 活动爱好者、需要处理大量图片素材的设计、剪辑等创意工作者。专业摄影师有 Lightroom、Capture One 这类成熟工作流，拾光舱不与他们争抢，而是补上爱好者「玩熟专业软件之前」的那一段空白。典型使用场景：出门前查天象决定是否外出、旅拍归来快速倒数据、几年后从几万张照片里找出某次活动的高ISO样片。

### 完整功能清单

#### 模块一：可信归档（v1.0.1 复赛改造）

**典型使用路径**：插入存储卡 → 选择目标仓库 → 开启可选归档/镜像 → 一键导入 → 在照片浏览页用多维筛选查找 → 必要时刷新 EXIF 补录元数据 → 用完整性校验确保仓库健康 → 清理孤儿 RAW 释放空间。

**1. 可信导入**
- 存储卡扫描，支持 SD / CF / XQD 卡自动识别挂载路径
- 并发 8 路复制 + SSE 实时进度反馈（总数、已处理、剩余时间、当前文件、百分比）
- **SHA-256 哈希校验**：导入时计算文件哈希并写入清单，命中已存在哈希自动跳过，杜绝重复入库
- 智能命名：按子文件夹分组，中文名保留为「文件夹名_原名」，英文名使用「文件夹名-序号」
- 重名冲突自动加 `-1/-2/-3` 后缀避免覆盖

**2. EXIF 时间归档（复赛新增）**
- 导入时可开启「按 EXIF 时间归档」，文件按 `category/YYYY/MM/` 结构自动归位
- 拍摄时间优先取 EXIF `dateTimeOriginal`，EXIF 异常或缺失时回退到文件修改时间
- 归档路径计算与文件复制解耦，归档失败不阻断主流程

**3. 双盘镜像备份（复赛新增，可选）**
- 导入时可指定镜像盘路径，主仓库复制完成后同步复制到镜像盘
- 镜像盘路径与目标仓库路径相同时自动拦截并提示，避免误操作
- 单文件镜像失败不阻断主流程，最终结果中单独统计 `mirrorSuccess` / `mirrorErrors`

**4. 仓库清单基础设施（复赛新增）**
- 每个仓库维护 `repo/.shiguang/manifest.json` 作为统一数据源
- 30 秒内存缓存 + hash 反向索引，列表查询、去重查找均为 O(1)
- 首次访问扁平结构仓库时自动初始化清单
- 提供「重建清单」能力，可从文件系统重新扫描并补全 EXIF

**5. EXIF 多维筛选（复赛新增）**
- 普通 / 高级筛选模式切换，普通模式与改造前完全一致，零学习成本
- 高级模式支持：日期范围、相机型号、镜头型号、焦距范围、光圈范围、ISO 范围、文件名模糊匹配
- 筛选项动态拉取（相机/镜头列表从清单 EXIF 聚合），无需硬编码
- 应用筛选后以标签形式展示当前生效条件，一键清除单条或全部

**6. EXIF 信息展示与补录（复赛新增）**
- 照片卡片展示：文件大小、拍摄时间（EXIF 优先，回退 mtime）、相机/焦距/光圈/ISO 参数摘要
- 详情面板：点击 EXIF 按钮查看完整元数据
- **批量刷新 EXIF**：针对旧版导入可能缺失 EXIF 的照片，一键补录元数据
- 场景化通知：已包含 EXIF、未读到有效 EXIF、补录成功等不同场景给出不同提示

**7. 仓库完整性校验（复赛新增）**
- 一键检查清单与文件系统的一致性，输出三类问题：
  - **缺失文件**：清单中存在但文件系统中已删除
  - **损坏文件**：文件存在但哈希与清单不一致
  - **未追踪文件**：文件系统中存在但未纳入清单

**8. RAW + JPG 智能配对与孤儿清理**
- 基于 EXIF 时间戳（±1s）与文件名主体的双因子配对，实测准确率超过 98%
- 覆盖 Canon、Nikon、Sony、Fuji 等主流厂商 RAW 格式
- 删除 JPG 时可同步删除同名 RAW，避免产生新孤儿
- 孤儿 RAW 一键扫描与批量清理

**9. RAW 缩略图与视频首帧预览**
- RAW 文件使用 sharp 生成缩略图，无需 Lightroom 即可浏览
- 视频文件使用内置 ffmpeg 提取首帧作为缩略图
- 不支持的格式自动生成带格式说明的占位图

#### 模块二：追光百宝箱（v1.0.2 复赛新增）

**典型使用路径**：打开追光页签 → 选择收藏城市 → 查看 7 天四类天象概率 → 选中高概率时段看蹲守建议 → 决定是否出门。

**10. 城市收藏夹**
- 16 个内置中国主要城市（北京/上海/杭州/广州/深圳/成都/重庆/武汉/南京/西安/昆明/哈尔滨/乌鲁木齐/拉萨/海口/三亚）
- 支持按城市名或经纬度添加自定义收藏城市
- 收藏夹持久化到 `config/lightHuntCities.json`
- 临时地点查询（"今日追光"）不入库，仅本会话生效

**11. 四类天象 7 天概率预测**

| 天象 | 算法核心 | 评分公式 |
|---|---|---|
| **朝霞** | 日出前后 1h 窗口的低云量 + 露点差 + 气溶胶 AOD | `0.5×cloud + 0.3×dew + 0.2×aod` |
| **晚霞** | 日落前后 1h 窗口，同朝霞算法 | 同上 |
| **雷暴** | CAPE 对流不稳定 + weather_code 雷暴代码 + 对流阵雨 | 低/中/高/很高/极端 五级 |
| **星轨** | 月相 illumination（suncalc 纯算法）+ 夜间云量 | `0.6×moon + 0.4×cloud` |

- 数据源：Open-Meteo 免费层（forecast + air-quality 双请求）+ suncalc 前端纯算法
- AOD 字段第 5-7 天预报缺失时自动 fallback 到 0.3 保守降权值，UI 灰底标记不确定性
- 配额预算：单城市单次预测 2 请求，重点 5 城 × 4 次/天 × 2 = 40 次/天，远低于 10k/天上限

**12. 24 小时甘特时间轴**
- 四泳道布局：朝霞 / 雷暴 / 星轨 / 晚霞
- 选中日期按小时展示各类天象的窗口区间与概率
- 星轨拆分为「日落后延续」和「深夜至黎明前」两段
- 一眼看清当天 24 小时蹲守节奏：白天雷暴 → 傍晚晚霞 → 夜里星轨 → 清晨朝霞

**13. 蹲守建议卡**
- 朝霞/晚霞：机位朝向（朝霞朝东偏南、晚霞朝西偏北）、日出/日落时间、最佳拍摄窗口
- 雷暴：高风险时段明细（CAPE 峰值、weather_code、对流阵雨量）、设备与安全须知
- 星轨：当晚月相 + illumination、月升月落时间、推荐拍摄窗口、500 法则单张最长曝光、堆栈张数建议

**14. W1 Dry-Run 算法验证**
- 上线前用 `scripts/light-hunt-dryrun/` 脚本对 4 城市 × 30 天 = 120 检查点验证 suncalc 月相合理性
- 8 个亚太城市 × 7 天验证 AOD 数据源覆盖率
- 发现并修复 PRD 原假设的 endpoint 错误（AOD 不在 forecast API，在 Air Quality API）
- 验证报告存档 `scripts/light-hunt-dryrun/W1-dryrun-report.md`

#### 模块三：系统体验

## 四、产品创作历程

### 灵感来源

我（开发者）是刚入门的摄影爱好者。玩摄影没多久，就遭遇了新手最容易低估的环节——**不是拍摄，是拍完之后的整理**。一次活动拍下来几百张 RAW + JPG，回家把存储卡往电脑上一插，就开始了漫长的折磨：拷贝没有进度条不敢中断、RAW 和 JPG 配对混乱、想找某张照片得逐盘翻文件夹、删照片时一不小心就留下半个孤儿。一整晚就这么耗进去了。

作为一名开发者，我的第一反应是：**这事为什么不能让程序干？** 市面上的后期软件都假设你「已经拷好了」，但拷贝和整理恰恰是最耗时的环节，却几乎没人管。于是决定自己动手做一款工具，把摄影师从「收尾工作」里解放出来。

初赛阶段我独立交付了 Demo，证明想法成立。但真正让产品发生质变的，是复赛阶段**邀请 catbohe（带我入门摄影的老哥）和大仙女加入团队**之后的事——catbohe 玩得比我久，平时就爱蹲朝霞、追雷暴、拍星轨，对"出门前该不该去"这个决策环节最有发言权，干脆主导开发了追光百宝箱；大仙女则承担测试与产品角色，在影像仓库模块的完善阶段把真实使用痛点一条条挑了出来。复赛的两次关键跃迁，一次由我主导开发、大仙女测试驱动，一次由 catbohe 主导开发、我辅助，整体进度由我统筹。

### 想解决的问题

三个摄影爱好者踩过的坑合在一起，痛点变得非常具体：

1. 系统复制没有进度反馈，几百 GB 不敢中断，怕拷到一半出问题
2. RAW 与 JPG 配对混乱，删一张忘一张，久了仓库堆满孤儿文件，硬盘越塞越满
3. 多硬盘 / NAS 没有统一视图，想找一张旧照片得逐盘翻，比拍的时候还累
4. Lightroom、Capture One 一年动辄上千，主战场是调色，对「导入 + 整理」几乎零帮助——但对爱好者来说，真正缺的恰恰是导入和整理这一环
5. **想蹲个朝霞/晚霞/雷暴/星轨，全靠经验+运气**，天气 App 只告诉你"今天多云"，不告诉你"今天 18:42 晚霞概率 78%"，错过窗口就是错过

### 为什么做这个方向

市场主流的后期软件都假设你「已经拷好了」，但拷贝和整理恰恰是最耗时的环节，却完全没人管。这是一块真实存在、又被忽视的空白。拾光舱不与 Lightroom 争调色，而是补上它前面的那一环——把素材安全、整齐地收进仓库，让摄影师把时间还给创作。

而追光百宝箱则把拾光舱的覆盖范围再往前推一步：从「拍完之后」延伸到「出门之前」。爱好者蹲守天象的现状是靠运气 + 靠感觉，天气 App 给的是"今天多云/有雷阵雨"，不是"今天 18:42 晚霞概率 78%，建议机位朝西偏北"。追光把"凭感觉蹲守"变成"按概率决策"。

### 从 Demo 到复赛完整版的两次跃迁

#### 跃迁一：v1.0.1 可信归档 + 可检索仓库

初赛阶段，我独立交付了一个能跑通「导入 → 配对 → 清理 → 预览」主链路的 Demo，证明想法成立。复赛一开始，我把 Demo 交给大仙女做真实归档测试——她用它整理了几次实拍素材后，把作为爱好者最直观的痛点倒了出来。这些反馈直接催生了 v1.0.1 改造方向：

1. **不可信**：拷贝过程没有校验，万一磁盘坏块或拷贝中断导致文件损坏，根本发现不了
2. **找不到**：照片越积越多后，想找某次活动的高ISO样片，只能按文件夹一层层翻
3. **不安全**：只有一份副本，硬盘一坏全没
4. **元数据缺失**：旧版导入的照片没有 EXIF 信息，筛选和归档都做不了

围绕这四个问题，复赛阶段我主导了「可信归档 + 可检索仓库」改造，核心是引入**清单服务**作为仓库的统一数据源。清单不仅是文件列表，还记录每个文件的哈希、大小、修改时间和 EXIF 元数据，并维护 hash 反向索引实现 O(1) 去重查找。

改造过程中有几个关键的技术决策：

- **归档路径与文件复制解耦**：归档路径计算只依赖 EXIF 和 mtime，不依赖复制结果，这样即使归档失败也能保证文件被复制到仓库，不丢数据
- **EXIF 异常不阻断主流程**：读取 EXIF 失败时返回 null，归档回退到 mtime，复制照常进行
- **双盘镜像单文件失败不阻断**：镜像复制失败只记录到 `mirrorErrors`，主仓库导入不受影响
- **筛选分普通/高级模式**：普通模式与改造前完全一致，`advancedFilter=false` 时 `appliedFilter=null`，零学习成本

这些决策的共同原则是：**核心流程永远先跑通，附加能力可以失败但不能拖垮主流程**。爱好者导入几百 GB 素材时，最怕的就是中途报错中断，宁可少归档几个文件，也不能让整个导入失败。

#### 跃迁二：v1.0.2 追光百宝箱

v1.0.1 改造完成后，catbohe 继续用，但很快反馈了一条新的痛点：**归档再好也只是「事后环节」，他真正每天头疼的是"今晚到底要不要出门蹲星轨"**。爱好者蹲守天象的现状是——打开三四个天气 App 看云量、翻月相表算月亮几点升起来、凭感觉判断值不值得出门，经常是扛着设备跑出去，到了才发现云层不对、月亮太亮，白跑一趟。

这条反馈让我意识到一个更深层的问题：**拾光舱的使用频次被锁死在「事件驱动」**——用户每周可能只打开一次做归档，应用停留在"归档工具"定位，日活天花板低。但摄影爱好者的真实工作流里，"出门前该不该去"这个决策环节每天都在发生，拾光舱对此零介入。

于是追光百宝箱由**catbohe 主导开发、我辅助**。他本身是前后端精通的开发技术大佬，又是最熟悉蹲守环节的摄影玩家，再加上 TRAE Work 的 AI 编程能力加持，追光从评分公式到前后端实现一条龙高质量落地。需要强调的是：**追光的评分依据不是任何人的个人经验，而是公开气象/天文数据源的提取与总结**——Open-Meteo 的 forecast + air-quality 双接口提供云量、露点差、CAPE、AOD 等气象参数，suncalc 库提供月相 illumination、月升月落等天文参数，评分公式（如朝霞 `0.5×cloud + 0.3×dew + 0.2×aod`、星轨 `0.6×moon + 0.4×cloud`）是把公开数据按摄影常识加权得出的，任何人都可以复现。最终对雷暴、朝霞/晚霞、星轨三类天象做未来 7 天的概率预测，覆盖爱好者"白天蹲雷暴 → 傍晚蹲晚霞 → 夜里蹲星轨 → 清晨蹲朝霞"的 24 小时蹲守周期。

**关键决策：把月相评分放前端，零网络成本**

星轨摄影对月相极度敏感：满月夜太亮会洗掉星星。最初考虑月相数据走后端请求，但调研后发现 `suncalc` 这个纯 JS 库可以本地算出月相 illumination、月升月落时间，~10KB 无依赖、零网络成本。

于是把星轨评分拆成两层：
- 后端只提取「夜间云量」（复用 Open-Meteo 同一次请求，零增量配额）
- 前端用 suncalc 算月相 + 云量合成最终评分

这样星轨基础版并入 v1.0.2 的成本远低于卷积云（卷积云需要中高空云量 + 湿度廓线，免费数据源粒度不够），是个高性价比的决策。

**关键决策：AOD 数据源纠错**

PRD 原假设气溶胶 AOD 字段在 Open-Meteo forecast endpoint，W1 dry-run 验证时发现 8 城全报错 "invalid String value"。排查后发现 AOD 在 Air Quality API（`air-quality-api.open-meteo.com`），且预报窗口只有 4.5 天。于是做了两个调整：
- 第 5-7 天 AOD 缺失时 fallback 到 0.3 保守降权值
- UI 第 5-7 天柱状图加灰底"不确定性更高"标记

这种「先 dry-run 验证再上线」的工程习惯，避免了上线后用户看到全是错的概率分。

### EXIF 刷新通知的打磨

有一个小细节值得提一下，最初是大仙女测试时挑出来的。最初实现批量刷新 EXIF 时，完成提示是「EXIF 刷新完成：成功 0 张，跳过 14 张，失败 0 张 未读取到有效 EXIF 样本」——技术上没问题，但大仙女作为真实用户一看就吐槽"这串字谁看得懂"。

这种打磨让产品从「能用」变成「好用」。也是从这一步开始，我意识到团队里有一个专门挑体验毛病的角色有多重要——开发者很容易对"技术上没问题"的提示自我满足，而真实用户的第一反应才是产品该打磨的方向。

### Windows 体验的打磨

## 七、技术方案分享

### 三层架构

```
┌──────────────────────────────────────────────┐
│  渲染层 (React + Vite + Ant Design + suncalc)   │  ← 界面、交互、月相纯算法
├──────────────────────────────────────────────┤
│  容器层 (Electron 主进程)                       │  ← 系统托盘、原生对话框、进程管理
├──────────────────────────────────────────────┤
│  服务层 (Node + Express)                        │  ← EXIF、哈希、清单、缩略图、追光评分
└──────────────────────────────────────────────┘
```

### 清单服务设计（v1.0.1）

每个仓库根目录维护 `.shiguang/manifest.json`：

```json
{
  "version": 1,
  "lastUpdated": "2026-07-22T00:00:00.000Z",
  "files": {
    "jpg/2024/03/DSC01234.jpg": {
      "hash": "sha256-...",
      "size": 12345678,
      "mtime": "2024-03-15T14:30:00.000Z",
      "exif": {
        "dateTimeOriginal": "2024:03:15 14:30:00",
        "model": "ILCE-7M4",
        "lensModel": "FE 24-70mm F2.8 GM",
        "focalLength": 70,
        "fNumber": 2.8,
        "iso": 800
      }
    }
  }
}
```

- **30 秒内存缓存**：列表查询、筛选项聚合走缓存，避免反复读盘
- **hash 反向索引**：`hash → relPath` 映射，导入去重 O(1) 查找
- **首次访问自动初始化**：扁平结构仓库首次访问时扫描文件系统生成清单

### 追光评分架构（v1.0.2）

```
┌─────────────────────────────────────────────────────────┐
│  前端 (suncalc 纯算法)                                   │
│  ├─ 月相 illumination / 月升月落 / 500 法则              │
│  └─ 星轨评分 = 0.6×moon_score + 0.4×cloud_score          │
├─────────────────────────────────────────────────────────┤
│  后端 (Open-Meteo 双请求)                                │
│  ├─ forecast endpoint: sunrise/sunset/cloud/dew/cape/wc  │
│  ├─ air-quality endpoint: AOD (4.5天 + 5-7天 fallback)   │
│  └─ 朝霞/晚霞/雷暴 评分 + 夜间云量提取                    │
└─────────────────────────────────────────────────────────┘
```

**关键设计：月相评分放前端，零网络成本**

suncalc 是纯 JS 库，~10KB 无依赖，月相数据本地算出，不增加 Open-Meteo 配额、不依赖网络。后端只提取「夜间云量」（复用朝霞/晚霞同一次请求），前端用 suncalc 算月相 + 云量合成最终评分。这是星轨基础版能低成本并入 v1.0.2 的关键。

### 容错原则

核心流程永远先跑通，附加能力可以失败但不能拖垮主流程：

- EXIF 读取异常 → 返回 null，归档回退 mtime
- 双盘镜像单文件失败 → 记录到 `mirrorErrors`，主仓库导入继续
- AOD 第 5-7 天预报缺失 → fallback 到 0.3 保守降权值，UI 灰底标记
- Open-Meteo 请求失败 → 显示上次成功时间 + 灰显过期数据 + 重试按钮
- PowerShell 不可用 → 回退到 `spawn('explorer', ...)` 兜底

## 八、开发心得

### 为什么选 Electron 而非 Tauri

摄影师的素材动辄几百 GB，导入流程要直接操作本地文件系统、读取存储卡挂载路径、调用原生文件夹对话框。Electron 对这类原生能力的支持更成熟，配合 electron-builder 能一键产出 macOS 与 Windows 安装包，对目标用户而言是「下载即用」，不需要折腾环境。

### 清单服务是关键取舍

最初考虑过两种方案：一是每次查询都直接扫文件系统，二是维护一个清单作为缓存。前者实现简单但查询慢、无法支持哈希去重和 EXIF 筛选；后者引入了缓存一致性问题，但带来了 O(1) 去重、多维筛选、完整性校验等能力。

最终选择清单方案，并用「完整性校验」能力反过来解决缓存一致性问题——用户可以随时一键检查清单与文件系统的差异。这是一个用「能力」换「复杂度」的决策，也是这个作品从「工具」升级为「仓库」的关键。

### 追光是产品定位的关键跃迁

v1.0.1 让拾光舱从「会拷贝的工具」升级为「可信任的仓库」，但使用频次仍被锁死在「事件驱动」——用户每周可能只打开一次做归档。catbohe 在 v1.0.1 完成后的一句"归档再好也只是事后环节，我真正每天头疼的是今晚要不要出门"，直接戳破了这个天花板。

v1.0.2 追光百宝箱把覆盖范围再往前推一步：从「拍完之后」延伸到「出门之前」。摄影爱好者蹲守天象的决策每天都在发生，追光让拾光舱从"按周打开"变成"按日打开"——这是从工具型应用向陪伴型应用的关键一跃。而这一跃之所以能落地，一方面是 catbohe 主导开发、把蹲守环节的需求吃透，另一方面是把评分建立在公开气象/天文数据源之上——不是"某个高手的私房经验"，而是任何人都能复现的公开数据加权，这才让"凭感觉蹲守"第一次有了被量化的可能。

### EXIF 双因子配对是核心算法

单纯靠文件名配对在连拍、重命名场景下会失准，单纯靠时间戳又无法区分同秒拍摄的多张照片。把两者结合——先按 EXIF 拍摄时间聚类，再在同名组内确认对应关系——是把准确率推到 98% 以上的核心。这个策略是和 TRAE 反复讨论、用真实素材验证后定下来的。

### 先 Dry-Run 再上线

追光功能涉及外部气象 API，算法公式有多个假设（AOD 在哪个 endpoint、suncalc 月相在高纬度是否 NaN、第 5-7 天 AOD 是否缺失）。上线前用 dry-run 脚本对 4 城市 × 30 天 + 8 城市 × 7 天做验证，提前发现了 AOD endpoint 错误，避免了上线后用户看到全是错的概率分。这种「先验证再上线」的工程习惯，是和 TRAE 一起做外部数据源集成时养成的。
